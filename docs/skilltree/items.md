# Skill Books, SP Books, the unlock show and the dungeon loot (`stitems`, 1.62.0)

Package `com.newuniverse.nusmp.skilltree.item` (the items and what reading them does), `com.newuniverse.nusmp.skilltree.loot` (the drops) and `com.newuniverse.nusmp.client.skilltree`
(`ItemsClient`, `BannerTimeline`). Assets: `assets/nusmp/textures/item/skill_book*.png`, `sp_book*.png`, `assets/nusmp/models/item/skill_book.json`, `sp_book*.json`, generated by
`tools/skilltree/gen_item_icons.py`. Data: `data/nusmp/loot_modifiers/skill_books.json`, one entry in `data/neoforge/loot_modifiers/global_loot_modifiers.json`. Config:
`nusmp-skilltree-loot-server.toml`. Design: `docs/skilltree/design.md` sections 4, 7 (loot), 9, 10, 11 are this builder's.

**Nothing here was run in the game.** The pure classes are unit tested (JUnit, 59 tests in this builder's files, three mutants killed, section 11), the game classes were type-checked
against the project's API stubs (section 11), the shipped assets are read and checked by `ItemsAssetsTest`, the sprites were rendered enlarged and looked at, and two in-game self-tests
(`tree.items.use`, `tree.items.loot`) are registered with the shared `SelfTests` registry so the CI server smoke test exercises the real thing. CI is the first real compile. Section 12
is the honest list of what is unverified.

## 3. WHY: the items (`SkillItems`, `SkillBookItem`, `SPBookItem`)

* **One Skill Book item for every route, the route named by a data component.** Items cannot be registered by a datapack but routes can, so a new magic (a JSON file) must never need a new
  Java class or a new item. `nusmp:skill_book_id` (a string: the route's `book` field) says which book a stack is; the route that lists it is the one it opens. The name, the cover colour and
  the lore all come from the route in the registry (the server's loaded copy, or the copy the server synced to a client), so a stack of a route that is later removed does not crash: it is
  named plainly "Skill Book" and reads as blank pages. *Rejected: an item per route (a code and asset change per magic), an NBT tag (data components are the 1.21 form and are network-synced
  by declaration).*
* **One SP Book item, the primer named by components.** `nusmp:sp_kind` and `nusmp:sp_amount` give the five primers their names, flavour lines and sprites without five registry entries, and let
  a datapack shop sell a stack with another number. The amount codec is `NON_NEGATIVE_INT`, so a hand-typed negative amount is rejected when the stack is parsed (and `BookRules` clamps as well).
* **Components are persistent and network-synchronised**, as the arc spawn egg's are: persistent so a stack survives a save, synchronised because the client needs them to tint the cover, pick
  the sprite and write the tooltip. Copied from `arc/ArcItems`.
* **Own `DeferredRegister.Items` and `DeferredRegister.DataComponents`, not the shared `NUItems.ITEMS`.** The shared register must be filled before the mod constructor attaches it, so every
  system that adds to it depends on the order of lines in that constructor. The skill tree starts from one line and attaches its own registers itself, so there is no order rule to forget. (No default
  component is put on the items' properties, so item construction does not depend on the component register's timing.)
* **The server decides, the client shows.** `use` calls `BookUse` only when `!level.isClientSide()`; on the client it only returns the success result (the arm swing). The tree is only ever
  changed on the server, through `SkillTreeApi`.
* **The glint (`isFoil`)** so a stack of knowledge is never mistaken for a plain item; rarity Rare for the Skill Book, Uncommon for the SP Book.
* **Factories `SkillBookItem.stack(bookId)` and `SPBookItem.stack(kind)`** are the ONE way a stack is built (creative tab, dungeon drops, the Black Market, the self-test). An unknown SP kind gives an
  EMPTY stack on purpose: a typo in a shop file must surface as a missing item, not as a silently sold book of something else. A book id no route lists still gives a stack (blank pages), so
  removing a datapack never deletes players' items.
* **Rule 7 (real 3D models in hand) is not applied to these two items.** The brief and design.md section 10 specify flat 16x16 sprites with a tintable cover layer ("one sprite pair serves every
  route"); a 3D model would need a texture per route. They are drawn as `minecraft:item/generated`. Flagged for the lead.

## 4. WHY: reading a book (`BookRules`, `BookUse`)

The order is always: ask the one door whether the engine is on (`SkillTreeApi.isEnabled()`: its writes do nothing while it is off), ask the rules (pure), ask the door to do it, look at what it
answered, and only then shrink the stack and tell the player. A book is never consumed unless the tree really changed: the switch is asked first, and only the API knows whether the Skill Points are
at their cap (the points before and after are compared).

| Book | What happens |
|---|---|
| Any book, the Skill Tree switched off (`enabled` false in the core config) | Action bar "The Skill Tree is switched off on this server."; nothing consumed. |
| Skill Book, route unknown (no route lists the id, or the stack has no id) | Action bar "The pages are blank."; nothing consumed. |
| Skill Book, route not yet unlocked | `SkillTreeApi.unlockRoute(player, route, true)`; on `OK` the book is consumed (not in creative), a chat line names the route; the API tells the listeners and the show plays. `DISABLED` (a race with the switch): "switched off", kept. `UNKNOWN_ROUTE`: blank. `ALREADY` (a race): treated as a copy. |
| Skill Book, route already unlocked | If `SkillTreeApi.duplicateBookGivesSp()` and the route's `duplicate_sp` is above 0: `addSp(duplicate_sp)`; the book is consumed only if the tree really gained points (at the cap it takes none: "Your Skill Points are full. The book stays closed.", the book stays). Otherwise "You already know the route X. The book stays closed.", kept. |
| SP Book | The amount from the stack (its own `sp_amount`, else the kind's; the gamble rolls with the stack's amount as its floor), clamped to 0..9999; 0 is blank. `addSp`; consumed only if the points really arrived. |
| Any of them inside the cooldown | Nothing happens. Every attempt that reaches the server starts a 20-tick cooldown on the item, so a held right-click cannot spam messages or race the unlock. |
| Creative reader | Gets the effect and keeps the book (`getAbilities().instabuild`). |

* The duplicate setting is the CORE system's (`SkillTreeApi.duplicateBookGivesSp()`), not a second copy of it in this system's config.
* Either hand works (the standard `use` flow offers both), where the design only said "main hand".
* `BookUse` never throws: the callers are item code, where an exception is a crash. A failure is logged and the player is told "The book would not open".
* The effects of an unlock are NOT played here (section 6).

## 5. WHY: the SP kinds and the gamble (`SpKind`, `JackInTheBox`)

The kind table is a closed enum in code on purpose: every kind needs its own sprite, name and flavour line in the resource pack, which a datapack cannot add, while the numbers are plain constants
the tests pin. The order is the creative-tab order and the numbering of the model overrides: new kinds are only ever appended, never inserted or renumbered.

| Kind (`sp_kind`) | SP | Name | Drop weight, monster | Drop weight, Guardian |
|---|---|---|---|---|
| `beginner_archery` | 2 | Beginner Archery Primer | 30 | 5 |
| `elemental_primer` | 3 | Elemental Primer | 25 | 15 |
| `magic_booster` | 5 | Magic Booster | 20 | 35 |
| `jack_in_the_box` | gamble, floor 1 | Jack-in-the-Box | 20 | 20 |
| `greater_primer` | 10 | Greater Primer (loot only, the shop does not stock it) | 5 | 25 |

The Jack-in-the-Box is the owner's gamble: a floor of 1 (the amount in the component), a **5% chance of a jackpot of 20**, otherwise 1 to 9 with the low numbers likelier
(weights 14, 14, 14, 14, 12, 10, 8, 8, 6 of 100), so the whole box pays **about 5.1 SP on average** (exactly 5.123) while any single opening is anywhere from the floor to the jackpot. The table is nine
integers, not a formula, so the curve can be read and changed in one place. A floor above 9 is clamped, so a hand-made stack cannot turn the box into a fixed giver of thousands.

Why the drop weights differ: an ordinary monster mostly drops the cheap primers and a Guardian mostly the good ones, so the boss feels like more than a bigger roll of the same dice. The means
are 3.87 SP per monster book and 5.82 per Guardian book (`SpKind.meanDrop`).

## 6. WHY: the unlock show (`UnlockFx`, `UnlockTiming`, `RouteUnlockedPayload`, `ItemsClient`, `BannerTimeline`)

* **A listener, not a call from the book.** `ItemsSystem.init` registers `UnlockFx::play` with `SkillTreeApi.addUnlockListener`. The API announces every successful unlock with its `announce` flag,
  so a route unlocked by a command, the shop or a quest gets the same show as one unlocked by a book, a quiet unlock (`announce` false) gets none, and a new way of unlocking cannot forget it.
* **Two stages, because a power-up has a build and a payoff.** All through the mod's own effect system (`VfxSpawn`; no vanilla particles, purged in 1.36.0), in the route's colour:

  | Tick | Server | Reader's client |
  |---|---|---|
  | 0 | page turn, enchantment-table whisper; `MAGIC_CIRCLE_EXPLOSION` on the ground (37 ticks: it charges for 60% of its life and bursts at tick 22; size 1.45, just under the 1.5 at which the effect shakes the camera); `MANA_CHARGE` motes drawn into the reader (22 ticks); the packet `nusmp:tree_route_unlocked` | waits |
  | 22 (`BURST_TICK`) | `DIVINE_PILLAR` (strike form: even seed), `LIGHT_FLARE`, `SPIRIT_AURA` following the reader for 70 ticks; the toast fanfare `UI_TOAST_CHALLENGE_COMPLETE`, a low `AMETHYST_BLOCK_CHIME` (pitch 0.5), `BEACON_POWER_SELECT` | the screen flash (the route colour mixed half toward white, 60% at its peak, gone in 16 ticks) and the banner |
  | 22 to 82 | | "ROUTE UNLOCKED" in large letters (3x, slamming in at 1.7x and settling), a line drawing itself under it, the route's name below at up to 1.9x, all fading out over the last 24 ticks: three seconds |

* **Why the numbers live in `UnlockTiming`.** The server and the reader's client play this together but never talk while it runs; the burst tick is a constant both read, and the circle's length is derived
  from it (`ceil(22 / 0.6) = 37`), pinned by a unit test, so changing the burst moves everything.
* **Why a small queue for stage two.** The effect system has no delay of its own. The queue is a list of (due server tick, player UUID, colour) drained from `ServerTickEvent.Post`; it holds no player
  object (a logged-out or dead reader simply gets no second stage) and is cleared on `ServerStoppedEvent`, so no state outlives a world. It is the only static mutable state of this builder.
* **Why the packet carries only the route id.** The client looks the name and colour up in its own synced registry, so the packet is a few bytes, cannot disagree with the rest of the UI, and a bad
  packet cannot make the client show anything a modified server could not already say. It is a `CustomPacketPayload` record with a `StreamCodec` (NeoForge 21.1 has no `SimpleChannel`), registered
  `optional()` on the mod bus like the mod's other cosmetic packets, the string bounded at 128 so a malformed packet fails at decode. The handler reaches the client class by name inside a lambda, so a
  dedicated server never loads it.
* **Why a GUI layer.** `RegisterGuiLayersEvent.registerAboveAll` is NeoForge 1.21's form of the old overlay (the System window does the same). The layer skips drawing while a screen is open or the GUI
  is hidden (a layer is not hidden by the game in those cases), and a draw that throws switches the banner off with one log line instead of one per frame. Text with an opacity under 4/255 is
  skipped, because the game would draw an alpha of 0 fully opaque.
* **Why the timing is a pure class.** `BannerTimeline` has no Minecraft type, so the edges that matter are unit tested: nothing before the burst or after the end, opaque for a while before the fade,
  the flash gone before the words, every value inside 0..1, over exactly at 60 ticks.
* **Tint, sprite and tooltip (`ItemsClient`).** The cover layer (tint index 1) is multiplied by the route's colour by an item colour handler (a neutral grey for an unknown route); the SP Book's
  sprite is chosen by an item property `nusmp:sp_kind` that the model's overrides read (0.1 to 0.5, because the game clamps a property to 0..1; the thresholds are half a step below, so no float
  rounding can make a kind miss its own sprite); one tooltip line "You already know this route." is added by an `ItemTooltipEvent` listener, because that needs the local player's synced tree and the
  item class is common code with no player.

## 7. WHY: the loot (`LootRules`, `RoutePick`, `LootDrops`, `LootVictims`, `SkillBookLootModifier`, `BossBookDrops`, `LootConfig`)

**The rule (pure, `LootRules.decide`).** Nothing drops outside the Mega-Dungeon dimension, for a death no player caused, on a Holy floor, in a gap between sectors, or from anything that is not an
ordinary monster or a sector Guardian.

| Victim | Chance |
|---|---|
| An ordinary monster (a vanilla-style `Enemy` or a Dungeon Master creature, neither a boss nor anyone's servant) standing in an **Abyssal** sector | `abyssalBookChance` **0.4%** of one route book, and independently `abyssalSpChance` **4%** of one SP Book |
| The Guardian of a sector of the **Abyssal** road whose last floor is a **boss floor** (a non-zero multiple of ten) | `bossBookChance` **30%** of a route book, and **always** `bossSpMin`..`bossSpMax` (**1 to 3**) SP Books |
| The Guardian of a **Holy** boss floor | nothing (the design: Holy floors are for the other loot) unless the config switch `holyBossDrops` is on |

The owner's own words ("Abyssal monsters, Decennial bosses") can be read as including the Holy bosses; the design says no; so that one case is a switch, default off. At the default numbers 1000 Abyssal
kills give about 4 route books and 40 SP Books (about 155 SP), a Guardian gives 0.3 route books and 2 SP Books (about 12 SP). One route book needs about 250 kills; with the four shipped routes (`loot_weight` 3, 2, 2, 2 in their JSON) the Fire Dragon
Slayer book is a third of them (about 750 kills for that one) and each of the others a bit over a fifth (about 1100 kills).

**Which route and which kinds** are decided apart from whether (`LootDrops`): the route is picked from `RouteRegistry.all()` weighted by each route's `loot_weight` (`RoutePick`: weight 0 never,
nothing positive means no route book, never a guessed index); the SP kinds by `SpKind.pickDrop` with the monster or the Guardian weights. At most one route book per drop, so "no duplicates within
one drop" holds by construction. The party credit: one drop per kill, to the loot context; nothing extra for the killer's party.

**Two doors, one rule.** The global loot modifier sees only what rolls a loot table. **The sector Guardian never does**: `LabyrinthGuardianEntity.dropFromLootTable` is overridden to do nothing
("No loot table: the Mana Core comes from the altar"). So the boss branch is served by `BossBookDrops`, a `LivingDropsEvent` listener at LOW priority (the door the dungeon's equipment drop and the Metal
Vessel reward already use for this very Guardian), which asks the same `LootRules.decide` and builds the same stacks through `LootDrops`. To make doubling impossible the modifier refuses a victim
that carries the Guardian's tag (`nusmp_sector_guardian`, `LabyrinthGuardianEntity.SECTOR_TAG`) even if a pack gave it a table. The listener acts only in the Mega-Dungeon, for a player's kill,
with `enabled` on and the `doMobLoot` game rule on, reads the sector it guards from the sector id the guard module stores on it (`nusmp_sector`; a test Guardian made by hand stores -1 and pays
nothing), and gives a route book that falls there glow, invulnerability and no despawn (a rare prize in a dark hall must not be lost to lava).

**Why a global loot modifier for the monsters.** It works on the loot that has ALREADY been rolled, whoever rolled it: every kind of monster of this mod or another gets the same behaviour with no
mob class, table or event hook edited, and nothing the table gave is replaced (the new stacks are added beside it: add the new, keep the old). It extends `LootModifier`, so the JSON carries the
standard `conditions` list, which is empty because the decision is in the code, in one place that can be read and tested (`data/nusmp/loot_modifiers/skill_books.json`:
`{"type": "nusmp:skill_books", "conditions": []}`). The codec is registered on the mod bus under `nusmp:skill_books` and switched on by the entry in the global list.

**Why `LootVictims` repeats three predicates of `GearDrops`.** `hostile`, `isBoss` and `isServant` are package-private there; the rule is "a skill book drops on exactly the kills that pay equipment",
so they are repeated line for line (an `Enemy` or a Dungeon Master creature, that is neither a boss by the economy's own tests nor anyone's servant) rather than editing another builder's class.
The sector, road and floor are read with the dungeon's own facade `MegaDungeon` (`polarityAt`, `floorAt`), never by parsing positions.

**Config** (`nusmp-skilltree-loot-server.toml`, section `[skill_books]`, plain `define` / `defineInRange`, read through a `get` helper that answers the default while the spec is not loaded):

| Key | Default | Range |
|---|---|---|
| `enabled` | true | |
| `abyssalBookChance` | 0.004 | 0..1 |
| `abyssalSpChance` | 0.04 | 0..1 |
| `bossBookChance` | 0.30 | 0..1 |
| `bossSpMin` | 1 | 0..10 |
| `bossSpMax` | 3 | 0..10 (lifted to `bossSpMin` if lower) |
| `holyBossDrops` | false | |

## 8. Assets (`tools/skilltree/gen_item_icons.py`)

A Pillow script, deterministic (no clock, no randomness), writing the textures into `src/main/resources/assets/nusmp/textures/item` and the models into `models/item`.
`--preview DIR` also writes enlarged previews (the Skill Book tinted in the four shipped routes' colours and the neutral grey of an unknown route, and the six SP sprites).

* `skill_book.png` (layer 0): the pages' right and bottom edges, the outline, the gold corners and a faceted gem in a gold setting. `skill_book_cover.png` (layer 1): the cover leather in neutral greys
  (highlight on top, a dark spine, a groove, a shadow side, six engraved marks), multiplied by the route colour on the client. The two layers never share a pixel (the cover is cleared under the gem and the
  corners), the cover holds only greys no darker than 104 (so the tint is clean) and its highlight is exactly white (so the brightest tinted pixel is exactly the route's colour); `ItemsAssetsTest` pins all three.
* `sp_book.png` (a stack with no known kind) and `sp_book_<kind>.png`: a green primer with a target and an arrow, a slate one with a four-colour elemental diamond, a violet one with a lightning bolt,
  a toy box with a spring and a clown's head (the gamble is not a book, so it reads as one), a crimson tome with a gold gem.
* `models/item/skill_book.json`: `minecraft:item/generated`, layer 0 the book, layer 1 the cover. WHY two layers: on `item/generated` the tint index of a quad is its layer number, so the cover (layer 1)
  is the only part the colour handler multiplies, and the gem and the fittings (layer 0) keep their own colours; one pair of sprites serves every route.
  `models/item/sp_book.json`: the default sprite and one override per kind (`nusmp:sp_kind` at least 0.05, 0.15, 0.25, 0.35, 0.45, ascending, because the last matching override wins) to
  `sp_book_<kind>.json`. WHY an item property read from the kind component rather than `custom_model_data` set by the factory: a stack made by hand (`/give` with only the kind) or by a datapack
  shop shows the right sprite too, because the sprite follows the component the stack really has.

## 9. Interfaces other builders and the lead rely on

* **The shop** builds stacks with `SkillBookItem.stack(String bookId)` and `SPBookItem.stack(String kind)` (the names the shop brief assumed); `SPBookItem.stack` returns an empty stack for an unknown kind.
  `SkillItems.bookIdOf / spKindOf / spAmountOf` read a stack; the SP kind ids are `SpKind.id()`.
* **Depends on the core builder's additions** (read from its finished worktree; none is in the committed contract): `SkillTreeApi.addUnlockListener(RouteUnlockListener)` (the top-level interface
  `com.newuniverse.nusmp.skilltree.RouteUnlockListener`, which this builder never names: it registers the method reference `UnlockFx::play`), `SkillTreeApi.duplicateBookGivesSp()` and
  `SkillTreeApi.isEnabled()`. Everything else it calls is in the contract: `unlockRoute`, `addSp`, `hasRoute`, `sp`, `of`, `RouteRegistry.all / byId / byBook`. The listeners are called on EVERY successful
  unlock with the caller's `announce` flag, each in a try/catch, so `UnlockFx.play` returns at once unless `announce` is true.
* **The creative tab** takes `SkillTreeSystem.creativeItems()` (already wired to `ItemsSystem.creativeItems()`): one book per route of the registry, one SP Book per kind.
* Getting a stack by hand: `/give @s nusmp:skill_book[nusmp:skill_book_id="nusmp:fire_dragon_slayer_book"]`, `/give @s nusmp:sp_book[nusmp:sp_kind="magic_booster",nusmp:sp_amount=5]`.

## 10. Decisions and alternatives rejected

* **Items on the shared `NUItems.ITEMS`** (like the arc egg): rejected, ordering (section 3).
* **A unlock effect called by the book:** rejected, a command, the shop or a quest would silently get none; a listener on the one door cannot be forgotten.
* **The Guardian's drop as a loot modifier:** impossible, it rolls no table (section 7); a second door with the same rule was chosen over editing the Guardian (another builder's class, and its "drops NOTHING" is
  a rule of its module).
* **Raising the chance with Looting or Luck:** rejected. The chances are the owner's numbers; Looting is already the lever of the equipment drops, and a second lever on a 0.4% roll would make the
  config numbers a lie.
* **A delayed task through the server's own task queue:** rejected, the vanilla `TickTask` tick is only an ordering stamp, not a delay; a small queue drained from the tick was chosen.
* **A per-route texture for the Skill Book:** rejected, one sprite pair plus a tint serves every route and every future datapack magic.
* **Own copy of the duplicate-book setting in the loot config:** rejected, two sources of one truth; the core's setting is read through the API.
* **A banner for bystanders too:** rejected, the banner is the reader's moment; bystanders see the circle, the pillar and the aura.
* **The System's toast for the banner (`SystemMsg`, `ToastKind`):** rejected, it is a small typed line that slides in from the left of the dungeon window and is only shown inside the dungeon
  dimensions; a three-second title card with a screen flash needs its own layer, and the unlock can happen anywhere (a book read in the Overworld).
* **Applying rule 7 (a 3D model in hand) to the books:** not done, see section 3.
* **Data-driven SP kinds:** rejected, each kind needs resource-pack assets a datapack cannot add (section 5).

## 11. What was verified

* **Unit tests** (JUnit 5, run with the shim runner `jt.sh`, 59 tests in 8 classes): `SpKindTest`, `JackInTheBoxTest`, `BookRulesTest`, `UnlockTimingTest`, `LootRulesTest`, `RoutePickTest`,
  `BannerTimelineTest`, `ItemsAssetsTest` (and the existing `SkillRouteTest` is untouched). They include seeded statistical checks (0.4% and 4% over a million kills, the Guardian's 30% and its mean of 2
  SP Books, the gamble's 5% jackpot and mean, the weights of the route pick), each within five standard deviations of a fixed seed.
* **Mutation check:** three deliberate breaks were made and each was caught: the Guardian's book chance reading the monster's field (two tests fail), the jackpot chance raised to 50% (three fail), zero
  weights no longer skipped by the route pick (one fails). The files were restored and the tests are green again.
* **Type-check** of every Java file of this builder against the project's API stubs (`tc_wt.sh`), with the core builder's real committed code (`tree/stcore`, commit c5361d4) laid over the contract
  so the calls to `addUnlockListener`, `duplicateBookGivesSp`, `isEnabled`, `unlockRoute`, `addSp` are checked against the real signatures: no error but the known stub artifact (`ItemEntity` is
  abstract in the stubs). A negative control (three deliberate wrong calls in a scratch copy) was reported by the same run, so the check does see errors in these files. A whole-tree compile
  with the test sources (`tc_full.sh ... test`, against the real JUnit API jars) reported nothing more in this builder's files than the same artifact and the calls to the core builder's additions
  (absent from the contract commit this branch was cut from). Note that script lists only files that are committed or new, so the two files this builder edited in place (`ItemsSystem`,

## 12. What is unverified (honest list)

1. **Nothing ran in the game.** No whole-project compile was possible here; the type-check is against API stubs that are incomplete (the one abstract-constructor error it gives for `new ItemEntity`,
   and classes the dumps do not describe).
2. **The banner and the show were never seen in the game.** The layout (a band, a 3x title that slams in, a rule, the name) was reasoned from the System window's code and checked as a rough Pillow mock
   (the same formulas as `BannerTimeline` and the same geometry as `ItemsClient.draw`, a stand-in font, not kept in the repository): the proportions, the flash, the fade and the colours hold together,
   but the game's own font, shadow and the real flash may need a tweak once seen. The effects' own looks (`DIVINE_PILLAR`, `LIGHT_FLARE`, `SPIRIT_AURA`, `MANA_CHARGE`, `MAGIC_CIRCLE_EXPLOSION`)
   are the existing layers'.
3. **The tint, the SP sprite property and the model overrides** follow vanilla 1.21.1's rules as I know them (tint index = layer index on `item/generated`; a registered property is clamped to 0..1;
   the last matching override wins); not seen in game.
4. **NeoForge applies global loot modifiers to every loot-table roll, including a monster's empty table** (assumed from the 1.21.1 source as remembered). A monster class that overrides
   `dropFromLootTable` (as the Guardian does) is invisible to the modifier by design.
5. **Stand-in players in the self-tests** are assumed to have a connection object that swallows packets (NeoForge's `FakePlayer` does); the show's packet sends are wrapped in a catch in any case.
6. **`SkillTreeApi.addUnlockListener`, `duplicateBookGivesSp()` and `isEnabled()`** are the core builder's additions, read from its finished worktree; until its branch merges this builder's branch does not compile
   alone (the type-check here used a scratch copy of the contract with those three stubbed).
7. **The route books' glow on the ground** (`setGlowingTag`) is only for the Guardian's drop; a book from an ordinary monster is an ordinary item entity (the modifier adds stacks, not entities).
8. **The economy numbers** (drop weights, the gamble table) are this builder's design on the owner's anchors (+2, +3, +5, gamble 1..9 with a rare 20, +10); they are config-free constants and may need
   tuning once players have played with them.
